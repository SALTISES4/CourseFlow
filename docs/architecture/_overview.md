# Architecture Overview

## Purpose

CourseFlow is a collaborative workflow authoring platform used to design, edit, and manage structured instructional workflows.

The system combines:

- structured workflow authoring
- hierarchical micro-step editing
- realtime collaborative editing via websockets
- server-authoritative persistence through REST APIs
- permission and locking systems
- workflow parent/child invalidation propagation
- frontend state synchronization with backend persistence

This document is intentionally biased toward **operational understanding of the running system** rather than theoretical architectural purity.

---

# Top-level architectural shape

The system is a **full-stack application** composed of two primary runtimes:

### Backend

A Django-based backend responsible for:

- persistence
- workflow mutation logic
- permission enforcement
- serializer/DTO boundaries
- websocket event coordination
- workflow hierarchy invalidation

Primary backend areas include:

- `course_flow/models/`
- `course_flow/serializers/`
- `course_flow/views/`
- `course_flow/services/`
- `course_flow/sockets/`
- `course_flow/routes/`

---

### Frontend

A React application responsible for:

- workflow editing UI
- local editing state
- websocket event consumption
- optimistic UI updates
- synchronization with backend persistence

Primary frontend areas include:

- `react/src/components/`
- `react/src/HTTP/`
- `react/src/state/`
- `react/src/hooks/`

---

# Runtime shape

The runtime system is composed of **two concurrent data channels**:

### 1. REST API channel (authoritative persistence)

All durable workflow state is persisted through the backend REST API.

Responsibilities include:

- workflow CRUD operations
- micro-step mutations
- permission enforcement
- serialization into canonical backend models
- returning normalized workflow payloads

REST is always treated as the **source of truth** for persisted workflow state.

---

### 2. Websocket realtime channel

The websocket system provides **collaboration synchronization**, not persistence.

Responsibilities include:

- broadcasting workflow mutations
- communicating field locks
- maintaining presence information
- propagating workflow parent/child invalidation messages

Realtime events allow multiple users to collaborate on the same workflow without waiting for full REST round-trips.

---

# Major subsystems

## 1. Workflow authoring subsystem

The workflow subsystem is the core domain of CourseFlow.

It manages:

- workflow documents
- hierarchical micro-step structures
- workflow relationships
- workflow editing operations

Key responsibilities include:

- loading workflows
- applying micro-step updates
- validating structure mutations
- serializing workflow structures for the frontend

Workflow editing operations are typically triggered by REST requests and then broadcast via websocket events.

---

## 2. Realtime collaboration subsystem

The realtime subsystem enables multiple users to collaborate on the same workflow simultaneously.

Key responsibilities include:

- managing websocket connections
- broadcasting workflow update events
- managing lock state
- tracking connected users
- emitting invalidation signals when workflows affect related workflows

Important property:

The websocket layer **does not own persistence**.

It reflects events generated by:

- REST updates
- user editing activity
- workflow relationship updates

---

## 3. Locking subsystem

Workflow editing requires protection against concurrent conflicting edits.

The locking subsystem manages:

- transient field locks
- editor ownership of locked elements
- lock updates via websocket messages

Locks are ephemeral and exist primarily in the realtime channel rather than permanent persistence.

---

## 4. Workflow relationship subsystem

Workflows may reference or embed other workflows.

Because of this, the system maintains **parent/child invalidation relationships**.

Responsibilities include:

- detecting workflow dependencies
- emitting update events when a referenced workflow changes
- notifying connected clients that dependent workflows must refresh

This mechanism prevents stale workflow references in collaborative editing sessions.

---

## 5. Permission subsystem

The backend enforces permission rules governing:

- who can view workflows
- who can edit workflows
- who can open websocket editing sessions

Permission checks occur at multiple points:

- REST endpoints
- websocket connection initialization
- mutation endpoints

This ensures that realtime collaboration respects the same authorization model as the API.

---

## 6. Frontend state synchronization

The frontend maintains **local editing state** that mirrors backend workflow data.

Responsibilities include:

- rendering workflow structures
- applying local edits
- sending mutation events
- processing websocket updates from other users

State must remain synchronized with backend persistence while supporting collaborative editing responsiveness.

---

# Current reality vs intended architecture

The codebase reflects an evolving system rather than a perfectly normalized architecture.

Important observations about the current snapshot:

- backend workflow logic is distributed across models, serializers, and service layers
- some websocket event semantics are implicit rather than formally documented
- naming conventions across serializers, DTOs, and workflow models are not always consistent
- frontend state management mixes persisted state with transient editing state
- realtime collaboration rules are partially encoded in websocket consumers rather than centralized services

These conditions are normal for a mature system that evolved organically.

However, they represent **important context for developers and coding agents modifying the system**.

Future changes should aim to:

- clarify boundaries between persistence logic and collaboration logic
- keep websocket events aligned with REST mutation semantics
- maintain a clear separation between backend authority and frontend UI state
- avoid duplicating workflow mutation logic across multiple layers
